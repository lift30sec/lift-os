# LIFT 日常運用コンテキスト v1.0

この文書は、楽天ROOM・Instagram・Threadsの日常投稿で最初に読む唯一の引き継ぎ資料です。過去のチャット全文を判断材料にしません。詳細仕様が必要な場合だけ、ここから参照先を開きます。

## 正本と読み込み順

1. 本書
2. `src/content/products.ts` と、今回扱う商品の `src/content/<product>.ts`
3. `docs/publication-log.md` の末尾120行
4. 未確定候補が必要な場合だけ `docs/discovery-log.md` の未処理部分
5. 判断に必要な場合だけ `docs/brand-spec.md`、`docs/content-spec.md`、`docs/design-spec.md`、`docs/automation-spec.md`

通常実行では、過去チャット、公開履歴の全件、全商品ファイル、過去のバッチ資料を読みません。商品台帳と公開履歴が会話より優先です。

## 運用目的

本人または家族が使った、暮らしの小さな手間を減らす商品を1実行につき1件公開します。公開枠は毎日12時と20時です。前日の繰越公開で当日枠を消化した扱いにはしません。

## 商品選定

- 公開済み商品IDと消化済み公開枠を除外する。
- 購入履歴の新しい順や未公開順ではなく、LIFTの目的への適合度で選ぶ。
- 日常的に使い、準備・片付け・収納・掃除などの手間が明確に減る商品を優先する。
- 使用前後の変化を6枚で具体的に示せ、読者が自宅で再現しやすい商品を優先する。
- 単純な詰め替え品、替えブラシなどの消耗品、交換部品、防災時だけ使う備品は原則候補から外す。日常の手間を減らす固有の工夫や意外な便利さが確認できる場合だけ例外とする。
- 「未公開であること」だけを採用理由にしない。候補に迷った場合は、投稿数を埋めるよりLIFTらしさを優先して停止する。
- 過去発言または商品データで使用確認済みなら再確認しない。
- 購入履歴は商品特定に使えるが、使用感の根拠にはしない。
- 本人の体験が不足するときだけ、口コミから便利な点を最大3案、惜しい点を最大1案提示し、承認か修正を求める。
- 事実、本人の体験、口コミ傾向、推測を混ぜない。
- 販売終了品と後継品、通常購入品とふるさと納税返礼品を明確に分ける。

## 公開文のルール

- 「本人」「本人宅」「本人が購入して使用」など内部確認用の言葉を公開文へ出さない。
- 使った商品は自然に体験を語る。口コミを本人の感想へ変えない。
- 一番便利になったことは1つへ絞る。
- 惜しい点は商品固有で購入判断に役立つものだけを最大1件掲載する。該当がない場合は欄を残し、「今のところ、特に惜しい点はありません。」と表示する。
- 「場所を取る」「サイズを測る」「定期的に手入れする」など当然の注意を機械的に惜しい点へ入れない。安全上重要なら残す。
- 誇張、根拠のない安全性・性能表現、競合商品の不必要な否定を避ける。
- 本人購入品へ広告表記を機械的に追加しない。商品提供や媒体ルールで必要な場合だけ付ける。

## 画像と6枚構成

承認済みの共通HTML/CSSテンプレートを使います。構成は表紙、困りごと、変化、正直レビュー、LIFT Insight、楽天ROOMへの導線です。

- 実物写真は求めない。
- 利用条件を確認できるメーカー公式・楽天アフィリエイト素材を優先する。
- 商品画像は切り抜きや文字重ねを避け、独立領域へ `contain` で配置する。
- 背景は商品に合う独自ビジュアルとする。2026-08-30のユーザー指示により、任意のAIラベルは追加せず、その確認・追加だけを理由に日常投稿を止めない。媒体側で必須と確認できる場合は従う。生成した背景を実際の使用写真と偽らない。
- 6枚目のROOM検索語はスマホ入力を考え、原則1語の短い名詞にする。
- ページ番号、文字切れ、解像度、商品名、型番、リンク、検索語を公開前に検証する。

## 公開と記録

楽天ROOM、Instagram、Threadsの順で公開します。Threadsは個別URLを取得できた場合だけ成功とします。

公開後、`docs/publication-log.md` へ商品ID、`publication_slot`、`actual_published_at`、3媒体のURLを追記します。商品台帳と調査記録を更新し、コミットしてmainへpushします。認証エラー時はローカルコミットを維持し、push未完了だけを報告します。

### GitHub認証エラーの切り分け

- 手動pushの繰り返しを避けるため、`docs/github-auto-sync.md` の限定送信ワーカーを準備した。登録・初回送信確認が済むまでは有効と扱わない。有効後は承認範囲を確認したコミットだけ送信依頼に記録し、対象SHAの成功結果を確認する。

- 制限された実行環境の `gh auth status` が失敗しただけで、認証切れやトークン無効を断定しない。
- 通常のWindows環境では資格情報ストア（keyring）の認証が有効でも、制限環境では別の結果になる場合がある。2026-08-30にこの差を確認した。
- 許可された手段で通常環境の認証状態を確認し、有効なら保存済み認証を使う。権限が必要な場合は所定の承認手順を使い、制限を迂回しない。
- 通常環境でも認証が失敗した場合だけ再認証を依頼する。通常環境で確認できない場合は「実行環境の制限で未確認」と報告する。
- `remote-https` が見つからない等のGit実行環境エラーは、認証エラーと分けて扱う。push成功は別途確認する。
- GitHubへのpushだけが未完了ならローカルコミットを維持する。SNSのログイン障害とは区別する。

## 停止条件

商品・型番、本人の評価、素材の利用条件、ブランド変更、法令・媒体規約のいずれかが不確かな場合だけ止めます。ログイン、CAPTCHA、媒体障害も停止対象です。それ以外は公開まで進めます。

## 省トークン運用

- 通常投稿は低い推論量で実行する。
- 調査や障害対応で必要な場合だけ推論量を上げる。
- ファイルは上記の順で必要箇所だけ読む。
- 中間報告を増やさず、公開後は商品名、便利な点、惜しい点、3URL、未完了事項だけ報告する。
- 会話内で確定した新ルールは本書か各仕様書へ保存し、以後チャット履歴へ依存しない。
